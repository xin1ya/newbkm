### 4.3 依赖方向（强制，由 lint 规则检查）

```
config ──► systems ──► (无依赖：纯 TS)
                ▲
core ◄── platform
  ▲
render ◄── world ◄── actors ◄── scenes ◄── ui
```

- `systems/` **不能** import `three`、DOM、`core/`、`render/` 等任何渲染或平台代码，保证能在 Node 中单测。
- 除 `platform/` 外，禁止直接使用 `localStorage`、`indexedDB`、`window.close`、`fetch` 外部地址。
- 跨模块通信优先用事件总线（`core/events`），避免 `world` 与 `ui` 互相 import。

## 6. 协作规范

### 6.1 分支与提交

- 主分支 `main` 永远可构建、可运行；不允许直接推送，一律通过 PR 合并。
- 分支名：`<类型>/<任务ID>-<简述>`，例如 `feat/SYS-003-damage-formula`。
- 提交信息：Conventional Commits + 任务 ID，例如 `feat(battle): SYS-003 implement type chart`。
- 类型：`feat` 新功能、`fix` 修复、`refactor` 重构、`test` 测试、`docs` 文档、`chore` 杂项、`art` 美术资源。

### 6.2 PR 检查清单

- [ ] CI 全绿（lint、类型检查、单测、构建）
- [ ] 纯逻辑改动有单测；渲染改动附截图或录屏
- [ ] **本文档已更新**：任务状态、负责人、新增目录（§4）、新增决策（§7）
- [ ] 没有违反依赖方向（§4.3）
- [ ] 新增资源符合模型规范（ART-002）并登记到资源进度表
- [ ] 如偏离设计文档，已在 PR 描述中说明，并补一条 ADR

### 6.3 完成的定义（DoD）

一项任务只有同时满足以下条件才能标 ✅：代码已合并到 `main`；有测试或可复现的验证方式；本文档已更新；没有遗留的 `TODO` 未登记为新任务。

### 6.4 命名约定

| 对象 | 规则 | 示例 |
|------|------|------|
| 文件（类） | PascalCase | `ChunkManager.ts` |
| 文件（函数集合） | camelCase | `damage.ts` |
| 配置 ID | kebab-case，带岛屿前缀 | `sprout-meadow`、`tide-ore-town` |
| flags | kebab-case，沿用 2D 方案已有名称 | `starter-chosen`、`badge-verdant`、`hm03-surf` |
| 任务 ID | 沿用 2D 方案 | `main-get-starter`、`side-zorua-forest` |
| 事件名 | `领域:动作` | `battle:start`、`quest:objective-complete` |

### 6.5 本文档的维护规则

1. 开始任务：填负责人，状态改 🟨。
2. 遇到阻塞：状态改 🟥，并在 §2.3 登记。
3. 完成任务：状态改 ✅，更新里程碑进度数，必要时更新 §4 模块状态。
4. 新增任务：在对应里程碑表格末尾追加，ID 顺延，不复用已删除的 ID。
5. 每个里程碑结束时，在 §8 变更日志中写一段总结。
